# GACODA MEMBER PORTAL, MEMBERSHIP FEES & PAYSTACK

Extend the GACODA website into a complete **membership management and payment platform**.

Members should be able to:

1. Apply for membership.
2. Create an account using their email and password.
3. Wait for administrator approval.
4. Log in after approval.
5. View their member profile.
6. Pay their annual membership dues.
7. View their payment history.
8. See their membership status.
9. Download/view payment receipts.
10. Update permitted profile information.
11. See when their annual membership expires.
12. Renew their annual dues when required.

Administrators must have complete control over membership, fees, payments and member accounts.

---

# 1. MEMBERSHIP FEES

Create a configurable fee system.

Initial values:

### Registration Fee

**GHS 20**

### Annual Membership Dues

**GHS 200**

However, DO NOT hardcode these amounts into the application.

Store them in PostgreSQL.

Administrators must be able to change them from:

`/admin/settings/fees`

---

# 2. REGISTRATION FEE TOGGLE

The administrator must be able to turn the registration fee ON or OFF.

Setting:

**Registration Fee Enabled**

Values:

`ON`

or

`OFF`

Default:

`ON`

When ON:

New applicants must pay:

**GHS 20 registration fee**

before their membership application can become fully active.

When OFF:

The registration fee becomes:

**GHS 0**

and the applicant does not need to make a registration payment.

The admin should be able to change this at any time.

---

# 3. IMPORTANT: FEE SNAPSHOTS

When a member starts a payment, save the fee amount that applied at that time.

For example:

If the annual dues are GHS 200 today and the administrator changes them to GHS 250 next month, an existing payment transaction should remain associated with the original GHS 200 amount.

Do not dynamically change historical transactions.

Store:

* Amount
* Currency
* Fee type
* Fee configuration version/reference
* Date
* Member
* Payment status

# 9. IMPORTANT PAYMENT RULE

Never trust payment information supplied by the browser.

The server must verify payments using Paystack.

Do NOT simply mark a transaction as successful because the frontend says payment succeeded.

Use Paystack's:

* Transaction initialization
* Transaction verification
* Webhooks

The server must verify:

* Transaction reference
* Amount
* Currency
* Payment status
* Relevant metadata
* Member/account association

Only then should the database mark a payment as successful.

---

# 10. PAYSTACK INTEGRATION

Integrate Paystack as the payment processor.

Use environment variables:

```env
PAYSTACK_SECRET_KEY=
NEXT_PUBLIC_PAYSTACK_PUBLIC_KEY=
PAYSTACK_WEBHOOK_SECRET=
```

Never expose:

`PAYSTACK_SECRET_KEY`

to the browser.

Use Paystack's official API from server-side/serverless code.

Create a payment abstraction so the payment provider can be replaced later if necessary.

For example:

```text
lib/payments/
  paystack.ts
  payment-service.ts
```

# 23. PAYSTACK WEBHOOK

Create a secure serverless endpoint such as:

`/api/payments/paystack/webhook`

The webhook must:

1. Receive Paystack events.
2. Verify authenticity/signature.
3. Find the corresponding transaction.
4. Ensure the transaction has not already been processed.
5. Verify the transaction details.
6. Update the payment record.
7. Update membership status/period where appropriate.
8. Record the event.
9. Return the correct response.

Implement idempotency.

If Paystack sends the same webhook multiple times, the system must NOT:

* Create duplicate payments
* Extend membership twice
* Create duplicate receipts

# 35. FINANCIAL SAFETY

Because this system handles money:

* Never trust client-side amounts.
* Never allow the browser to determine the payment amount.
* Always retrieve the current fee from the server/database.
* Store the amount associated with the transaction.
* Verify Paystack transactions server-side.
* Verify webhook authenticity.
* Implement idempotency.
* Never expose secret keys.
* Never log payment secrets.
* Never store card details.
* Never store CVV.
* Never store Paystack credentials in PostgreSQL.

The frontend may display the current amount, but the server must determine the actual amount to charge.
